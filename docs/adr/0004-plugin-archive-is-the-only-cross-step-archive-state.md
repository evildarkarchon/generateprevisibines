# The plugin archive is the only state carried across the archive steps

Status: accepted. Amended 2026-10-02: leftover work folders are now cleared at the start of every Workflow Run rather than stopping the run, and cleanup failures are Build Warnings. The second rule below records the change, decided while writing the Archive spec (issue #45). Amended again 2026-10-02 after review: clearing a leftover folder whatever it held could silently destroy the only copy of precombines, previs or a new archive left by a crash. So a Workflow Run now first moves back what a restore list says the folder holds the only copy of, and sets aside any folder it cannot restore instead of deleting it. The same review found that the start-of-run handling would also act on a folder another run was still using. [ADR-0005](0005-one-workflow-run-per-installation.md) rules that out with a per-installation lock. This amendment also moves BSArch staging into a `staging\` subfolder of the work folder, so that the restore list is never packed.

Step 3 (Create BA2 from Precombines) and Step 8 (Add Previs to Archive) both write `<plugin> - Main.ba2`, and Step 8 has to keep what Step 3 put there. Neither Archive2 nor BSArch can append to an archive in place. The batch works around that differently for each tool. Archive2 recovers the precombines *from the archive*: Step 8 extracts it into `Data`, waits 5s, deletes it and repacks `meshes\precombined,vis`. BSArch recovers them *from disk*: Step 3 moves the loose precombines into `<fo4>\BSArchTemp` and leaves them there, so Step 8 can move `vis` into the same tree and repack the whole thing. That leaves cross-step state outside the archive on the BSArch path, and the state is fragile. Step 1 clears `BSArchTemp`, but only on a fresh run (batch line 262). A `-bsarch` resume at Step 8 whose `BSArchTemp` is missing — deleted by hand, or Step 3 ran with Archive2 — packs `vis` alone over the archive and silently loses the precombines. Leftover staging from another plugin gets packed into the next one.

We make the plugin archive the only state either tool carries between the archive steps. Step 3 packs the precombines and removes the loose files, for both tools. Step 8 rebuilds the archive as its old contents plus `vis`. Archive2 keeps the batch's extract → 5s wait → repack exactly. BSArch unpacks the archive into a staging folder, moves `vis` in, waits 5s and packs. Both BSArch generations have `unpack` (0.9x, xEdit ≤ 4.1.5p, and 1.0, xEdit 4.1.5q); the batch simply never called it. So no BSArch version detection is needed, and a resume at Step 8 needs only the archive and `vis`.

Two rules govern the work folder. The first ensures that no failure leaves the user without their archive. The second ensures that leftover state never blocks a build, is never packed into one, and is never deleted while it holds the user's only copy of something:

- **Build elsewhere, check, then swap.** Both tools write the new archive into a run-owned work folder beside `Data` (`<fo4>\ArchiveWork`) under its final name. The archive-exists check runs on that file, because `Archive2 -c` with no sources exits 0 and creates nothing. Only after that check passes is the old archive in `Data` replaced. The batch deletes the archive before repacking (440 → 442), so a failed repack there leaves loose files and no archive, a state the workflow cannot resume from cleanly.
- **Restore leftover work, then clear it, and never build on it.** ADR-0005 allows one Workflow Run per installation, so a work folder found at the start of a run is never in use. It is left over from an earlier run, which crashed or stopped on a failed step. It may hold the user's only copy of their precombines (BSArch Step 3 moved them in), their previs (BSArch Step 8 moved `vis` in) or the new archive (the swap deleted the old one but had not moved the new one in yet).
  - **The work folder has three parts.** `staging\` is the tree BSArch packs: Step 3 moves the precombines to `staging\meshes\precombined`, and Step 8 unpacks into `staging\` and moves `vis` to `staging\vis`. `<plugin> - Main.ba2` is the built archive, which both tools write beside `staging\`. `restore.txt` is the restore list. BSArch packs only `staging\`, so neither the archive nor the list can end up packed.
  - **The restore list** names what the folder may hold the only copy of, and where each item goes back in `Data`:
    - The step writes it empty right after creating the work folder.
    - Before the step moves anything out of `Data` into the work folder, it adds an entry for that move.
    - Before the swap deletes the old archive, it adds an entry for the new archive.
    - An unpacked archive copy, or an archive that never reached the swap, is never listed. A crash can leave these half-written, and `Data` still holds what they were made from.
    - A move-back leaves the list alone, because the restore skips an entry whose item is no longer in the folder. The step removes the whole list as soon as the swap succeeds, before the rest of its cleanup, because the staged sources are still in the folder at that point and are now in the archive too.
  - Every Workflow Run handles all of its work folders (`ArchiveWork` and any `ArchiveWork.<n>`) after preparation and before its first step. It does this whatever the resume point:
    - **Restore.** Each listed item still in the work folder is moved back to its place in `Data`, and a Build Warning names what was restored. If an entry's item is not in the work folder, the entry is skipped, because the crash came before the move. The new archive is moved back only if `Data` has no Plugin Archive. If `Data` has one, the swap never deleted it, and the new archive is not needed, because its sources are either still in `Data` or restored with it.
    - **Set aside.** If a listed item cannot be moved back, the folder is renamed to the first absent `ArchiveWork.orphaned.<n>`, and a Build Warning names it and the items it still holds. That happens when something already exists at the item's place in `Data`, when the move fails, or when the list cannot be read or parsed. The port never deletes, builds in or packs an orphaned folder. The user recovers it or deletes it.
    - **Remove.** A folder with no list, an empty list, or nothing left to restore is removed. What remains in it is only copies and unfinished output.
    - If a folder cannot be renamed or removed (for example, because of a usvfs or antivirus lock), a Build Warning names it and the run continues.
  - This replaces the batch's deletion of its staging folder in the Step 1 preamble (line 262), which ran only on a fresh run.
  - Each archive step then builds in the first work-folder name that does not exist: `ArchiveWork`, then `ArchiveWork.1`, `ArchiveWork.2` and so on. That way the new archive is always built in a clean folder, because BSArch packs the whole staging tree. A stuck folder never stops the run, and orphaned names never match the pattern.
  - Removing the work folder or the loose source folders once a step is done is cleanup as well: a failure there is a Build Warning, never a stop.
  - Three failures still stop the run and leave the work folder in place:
    - A failed move-back after a BSArch failure.
    - A failed swap.
    - A failed removal of the restore list after a successful swap. A stale list would put superseded loose files back into `Data` on the next run.
  - The first two may leave the user's only copy of their precombines, previs or new archive in the work folder. Their error names the folder and says the next run will move the listed files back, or set the folder aside if it cannot.
  - The port never creates, reads or deletes the batch's `BSArchTemp`.

Step 2 stops on zero meshes, and Step 3 stops when there are neither loose meshes nor an archive, so an archive missing at Step 8 means something outside the run deleted it. A `vis`-only archive is a broken build, because previs refers to the precombines. Step 8's `:ArchiveOnly` fallback (424, 445) is therefore dropped, and a missing archive at Step 8 stops the run. That also removes the BSArch `Meshes\vis\*.uvd` bug, which came from that fallback staging `vis` under `BSArchTemp\Meshes`. If the extract or unpack yields no precombined meshes, the run stops before the old archive is touched, instead of rebuilding from `vis` alone (441 → 445).

## Considered options

- **Batch parity: `BSArchTemp` carried from Step 3 to Step 8.** Rejected for the resume data-loss path above, and because it would need rules for what every resume point inherits from a folder the run cannot validate.
- **BSArch 1.0's multi-source pack, `old.ba2+Data\vis → new.ba2`.** No staging at all, but only xEdit 4.1.5q ships BSArch 1.0. Which BSArch a user has follows their xEdit, so 0.9x would still need one of the other designs, plus a version probe to choose between them.
- **Stop the run on a leftover work folder, and never clear it** (this ADR's original rule). Rejected when the spec was written. A crash would block every later archive step until the user deleted the folder by hand, and a folder the tool cannot delete would block the build outright. Handling the folders at the start of every run, with a fresh sibling as the fallback, keeps the build moving and still never packs stale state.
- **Clear every leftover work folder, whatever it holds** (the first amendment). Rejected on review. A detected failure could tell the user to recover their files first, but a crash (a killed process, a power loss) never reaches that message. During BSArch Step 3, during BSArch Step 8 and between the swap's delete and its move, the work folder holds the only copy of the precombines, the previs or the new archive. The next run deleted it silently, which cost a rerun of the Creation Kit step that made it, and a resume then stopped with no hint why.
- **Restore by content alone, without a restore list.** Rejected because content does not show where a file came from. BSArch Step 8's unpacked precombines look the same as BSArch Step 3's moved ones, and a `.ba2` half-written by a crash looks the same as one that passed the check. Restoring by content would put duplicate loose meshes or a broken archive into `Data`.
- **Set every non-empty leftover aside, with no restore.** Simpler, but every resume after a crash would need the user to move files back by hand, and every BSArch Step 8 crash would set aside gigabytes of unpacked copies.

## Consequences

BSArch Step 8 pays an extract it did not pay before, and BSArch `unpack` is new to this workflow. Its round-trip fidelity is a Windows experiment the Archive spec waits on. The batch's BSArch path has no MO2 wait. The port adds 5s before each BSArch pack, because under MO2 files moved out of the virtual `Data` may not have settled when BSArch reads the staging folder, which would produce an incomplete archive.

The restore list closes the crash window, but it leans toward duplicates rather than loss. If a crash lands between a successful swap and the removal of the list, the next run moves loose files back into `Data` that the archive already holds. A Build Warning names them. A directory move that a crash cut short leaves its `Data` place partly filled, so that folder is set aside rather than merged. Orphaned folders can hold gigabytes. The port never prunes them, and the Build Warning that names one is the user's only prompt to deal with it.
