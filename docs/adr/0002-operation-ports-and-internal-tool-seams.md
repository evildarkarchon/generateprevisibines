# Operation ports are data, and the tool seams under them are internal

Status: accepted

ADR-0001 said Creation Kit, FO4Edit, archive, prompt and wait behavior "sit behind named adapters". Only Creation Kit and one prompt ever did. This records how the rest of that intent is delivered for Creation Kit, and settles the questions ADR-0001 did not reach. It refines ADR-0001; it does not reverse it. The Workflow Operation still owns the step's domain flow, and that is still why `ToolRunner` is gone.

What a Workflow Operation is handed is data, not an interface. `OperationAdapters` was a trait over the whole set, and nothing was ever substituted at that level: there is one such set in production, and the tests never wanted a different one either — they assembled the same three ports and varied what sat inside each. The criterion for whether a trait is a seam is not how many types implement it but whether anything is ever swapped there, and there nothing was. That is an indirection, not a seam. What does get swapped is the ports themselves — `FileSpace` for `InMemoryFileSpace`, `ProcessRunner` and `Wait` for their recording counterparts, `Prompts` for a recording double — and each of those swaps buys a specific assertion. So `OperationPorts` is a plain struct of those ports. `ck` on it is a concrete `&CreationKitOps` rather than a `&dyn CreationKit` by the same criterion, and it is the sharper case: nothing would be swapped there either, because the tests deliberately go underneath it.

`ProcessRunner` and `Wait` are internal seams, private to the tools layer, and are deliberately not fields on `OperationPorts`. A Workflow Operation states build meaning before an adapter is chosen; how a process starts and how long MO2 is given to sync are not build meaning, they are how the Creation Kit episode keeps the ordering `docs/workarounds.md` §2 and §3 require. A deep module is allowed internal seams that its own tests substitute at without those seams becoming part of its interface — that is what makes the seams cheap to widen later. They are crate-visible only so that the Step 1 tests in `src/workflow/` can reach the recording adapters.

Tests substitute at `ProcessRunner` and `Wait`, not at a `CreationKit` port. This is the decision most likely to be re-litigated, so the reasoning is worth stating fully. Faking a CK port is the conventional move and it is the wrong one here, for two reasons. First, the only thing that would ever implement it besides `CreationKitOps` is the fake itself, so the trait would exist solely to enable one test — and that test is what the second reason argues against. Second and decisively, it tests nothing that was untested. The risk in the Creation Kit episode is not "does a Workflow Operation call CK" — that is trivially true and would be all a CK fake could assert. The risk is the *composition*: the DLL guard disabling ENB/ReShade before the spawn and restoring on every exit path including an error, the stale log being deleted so what is read back belongs only to this run, the 10-second MO2 delay actually happening after the exit, the log being read once and folded into the session log, and a log that exists but cannot be read raising an error instead of collapsing into "no log". That ordering is precisely what had never been tested, and every one of those obligations is a required workaround rather than incidental sequencing, so a regression in any of them is silent. A CK fake replaces all of it. Substituting one level lower runs the real `CreationKitOps` under a Step 1 test and puts the whole composition under assertion, while the recording `Wait` proves the mandated delay happened rather than compiling it away.

The Creation Kit adapter owns the log lifecycle and the exit-code policy; the Workflow Operation owns the success criteria. Both halves follow from ADR-0001's rule that success criteria belong to the step and not to the tool adapter, and the batch's own shape is the evidence for where the line falls. The log scan is per step in both predicate and severity: after `GeneratePrecombined` the batch scans for `OUT OF HANDLE ARRAY ENTRIES` and treats a hit as fatal (lines 270-271), after `GeneratePreVisData` it scans for `ERROR: visibility task did not complete.` and treats a hit as a warning it continues past (lines 312-313), and `CompressPSG` and `BuildCDX` scan the log for nothing at all. Nothing uniform is available to hoist into the adapter, so `CkRun` hands back the log contents and lets the step judge them. The non-zero exit is the mirror image: the last statement in `:RunCK` before it returns is a single line — `IF %Err_% NEQ 0 echo WARNING - %1 ended with error %Err_% but seemed to finish so error ignored.` (line 463) — applied identically to all four operations. That downgrade is settled inside the adapter and `CkRun` carries no exit status, because a field no caller may act on differently is an invitation to act on it differently.

The FO4Edit and archive adapters are deferred to Phase B, to be designed against real callers. Neither can be designed honestly now. `ProcessRunner`'s current interface is synchronous spawn-and-wait, which is all Creation Kit needs; FO4Edit needs an async spawn plus control of the resulting process handle — `AppActivate`, `CloseMainWindow`, `TaskKill` — and an unbounded poll for the script's completion marker, and guessing that widening without the caller in hand would shape the port around an imagined FO4Edit rather than the real one. The archive adapter has a worse trap: "append" is a fiction for both tools. Archive2 has no append and the batch extracts the whole archive and re-packs it; BSArch has no append either — the batch moves the new files into a `BSArchTemp` staging tree and packs that tree fresh. An `ArchiveOps::append` designed now would name an operation neither tool performs, and the two tools' real operations are not the same shape.
