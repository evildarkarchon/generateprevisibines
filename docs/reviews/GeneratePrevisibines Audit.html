GeneratePrevisibines Audit

23 November 2026 Commit 0178a3b on main Batch reference V2.99 Rust 1.100, edition 2024

The port is in good shape. All eight workflow steps are implemented and well tested, the code documents its reasoning, and the tooling is nearly clean. The audit found one high-severity parsing bug, a set of medium parity gaps where the port behaves worse than the batch on a failure or resume path, a layer of rollout scaffolding that can no longer run, and entry-point documentation that still describes an unfinished project.

Nothing in the repository was modified. None of this was run against a real Fallout 4, Creation Kit or MO2 install, so findings that depend on how those tools behave are marked plausible.

Start here

Six changes, in priority order. The first five are small, and each removes a way for a run to lose work or mislead whoever is reading the output.

  1. Parse ; comments in CKPE config values. B1
    On the .ini CKPE variant the Creation Kit log is never found, so the handle-array stop and the visibility-task warning are silently skipped.
  2. Stop offering to delete precombined meshes on a fresh run, and remove the Yes default. B2
    The batch hard-stops here. The port asks, and a stray Enter deletes hours of Creation Kit output.
  3. Decide how DLLs get restored when Drop does not run. B3
    The latest commit set panic = "abort". Combined with no Ctrl-C handling, ENB and ReShade DLLs can stay disabled after a stopped run. The code and docs still promise otherwise.
  4. Append to the session log on a resume instead of truncating it. B4
    Resuming at Step 6 after a failure erases the log that explains the failure.
  5. Correct the documentation that contradicts the code or the tools. P1 P2 P8
    AGENTS.md tells agents to preserve PowerShell keystrokes, which the port replaced with window messages. The README describes a scaffold that no longer exists. ADR-0004, the glossary and the episodes reference say BSArch cannot append, which is wrong and is what the Step 8 unpack-and-repack design rests on.
  6. Remove the partial-rollout machinery. D1
    With all eight steps registered, StepNotImplemented, the planned/runnable split and about fourteen tests cover plans production cannot build.

B1
Highverified

CKPE config values with a trailing ; comment are mis-parsed

src/validation.rs:91–134 · batch lines 109, 129–133
// port: cuts the log value at '#' only, and compares the whole handle value
let log = value.split('#').next().unwrap_or(value).trim().trim_matches('\'')...
return value.trim().eq_ignore_ascii_case("true");

:: batch: both comment characters are delimiters
for /F "tokens=2 delims==#;" %%a in ('Findstr /I /C:"%CKPELogSetting_%=" ...
Impact
CKPE's .ini config puts a ; comment after each setting (the reviewer saw this in the CKPE 0.3 and 0.5 files on this machine). The log name becomes ck.log<TAB>; Print log output…, which is not a file. The Creation Kit log is then never found, so the OUT OF HANDLE ARRAY ENTRIES stop and the visibility-task warning are skipped. sOutputFile=none ; … stops counting as "none", so the "CK Logging not set" stop is skipped too. The handle-limit warning fires on every run. Double-quoted TOML values keep their quotes.
Fix
One value normaliser used by both functions: cut at the first # or ;, trim, strip one matching pair of quotes. Add fixture tests built from real CKPE .ini and .toml files.

Mediumverified

DLL restore depends on Drop, which no longer runs on a release panic and never ran on Ctrl-C

Cargo.toml:45 · src/tools/dll.rs:25, 114–143 · docs/episodes.md:89–93 · batch 362–367
Impact
Commit 0178a3b set panic = "abort"; its message notes that Drop impls then do not run. Mediumverified

src/run.rs:169–175 · src/logging.rs:62–70 · batch 265–266
Impact
The batch deletes the log and writes the header only inside Step 1's preamble; a resume at Steps 2 to 8 appends. The port calls init_session_log unconditionally in prepare. B5
Mediumverified · reproduced

A quoted -FO4: path ending in a backslash swallows the rest of the command line

src/cli.rs:247–251 · batch 480, 497
> generateprevisibines.exe "-FO4:Q:\Nope Dir\" MyMod --dry-run
ERROR - could not open the installation lock Q:\Nope Dir" MyMod --dry-run \GeneratePrevisibines.lock: ...
Impact
Windows argument parsing reads \" as an escaped quote, so the plugin name and every later flag join the path. --dry-run is lost and the call becomes a real run attempt. The batch is immune because it strips quotes textually. Its header tells users to quote paths with spaces, and tab completion adds the trailing backslash.
Fix
A " is never legal in a Windows path or plugin name. When a normalised argument contains one, re-tokenise the tail or stop with a hint to drop the trailing backslash.

Mediumverified

A relative --FO4 directory is never made absolute

src/discovery.rs:142 · src/toolchain.rs:61 · src/tools/fo4edit.rs:224–227, 437–439 · src/tools/archive.rs:227–312
Impact
FO4Edit is started with %TEMP% as its working directory and given -D:<override>\Data verbatim. With -FO4:. from the game folder, Step 1 runs Creation Kit to completion and Step 2 then points FO4Edit at %TEMP%\.\Data and stops with the missing-modules fatal. B7
Mediumverified

The plugin-name character rule is keyed on "contains a space", not on where the name came from

src/validation.rs:50–58 · src/config.rs:169–193 · batch 490
Impact
The batch applies its [a-z0-9_.] rule to every command-line token and to no interactive name. The port applies it to any name without a space. Two consequences. In Filtered mode a name with a space skips all character checks, so "..\..\My Mod" or an absolute path resolves outside Data and %TEMP%, and an accepted seed copy writes there. And a space-free interactive name such as My-Mod is rejected, though the batch accepts it, so the port cannot build that plugin by any route. An empty name also passes and yields Data\.esp.
Fix
In every mode and from every source, reject an empty base, path separators, .., Windows-illegal characters and a trailing dot or space. Apply the token rule only to command-line names, or drop it.

D8
Mediumverified against BSArch v1.1 usage text · not run

BSArch Step 8 unpacks the whole archive, though BSArch can pack an archive plus a folder directly

src/tools/archive.rs:218–231, 263–312 · docs/adr/0004 (Considered options)
BSArch v1.1, as installed beside xEdit on this machine
BSArch.exe pack <source1+source2+...> <archive> [parameters]
  <sources>    Path to the source folder, file or archive with file(s) to pack
               Files from later source win on matched file names
Impact
With -bsarch, Step 8 unpacks the Plugin Archive into ArchiveWork\staging, moves vis in, waits 5s and packs everything again. For a large precombine archive that is gigabytes of extract and recompress, and ADR-0004 itself lists the fidelity of an unpack round trip as an open experiment. BSArch can instead take the existing archive and a folder as two sources of one pack. ADR-0004 considered exactly this as "BSArch 1.0's multi-source pack" and rejected it only because BSArch 0.9x (xEdit 4.1.5p and earlier) lacks it.
Fix
Revisit that rejection. Packing "Data\<plugin> - Main.ba2"+"ArchiveWork\staging" into ArchiveWork\<plugin> - Main.ba2, with only vis moved into staging, keeps both ADR rules (build elsewhere, check, swap; the archive as the only cross-step state) and drops the unpack. Decide what happens on BSArch 0.9x: require 1.0 or later with a clear error, or keep unpack-and-repack as a fallback behind a version probe. Before committing, confirm on a real archive that the result holds meshes\precombined and vis at the right paths. Whether the output may be the same file as a source is untested, and the swap rule means it never needs to be.

The ADR opens with "Neither Archive2 nor BSArch can append to an archive in place". episodes.md says "BSArch has no native append" and lists append as "also not a verb". future-features.md says "BSArch has no append verb either". BSArch has no verb named append, but its pack accepts an existing archive as a source beside folders, so it adds files to an archive in one command (D8 quotes the usage text). What these documents describe accurately is the batch, which never uses that and stages through BSArchTemp. They then state a property of the batch as a limit of the tool, and the port's unpack-and-repack design for BSArch rests on it. AGENTS.md:27 ("community tool with append support") and README.md:188 are correct. The first version of this report had this backwards: it trusted these four documents and marked those two lines as wrong.
Fix
State the capability the same way in all of them: BSArch 1.0 and later can pack an existing archive plus new files into a new archive; the batch does not use it. Rewrite ADR-0004's opening sentence and its rejected option to say the choice was made for BSArch 0.9x compatibility, not because the tool cannot do it. Leave the glossary's "rebuilds rather than adds to" wording until D8 is decided, because it describes what the port does today.

What the codebase does well

Worth protecting while the findings above are addressed.

  • Tools sit behind ports, and tests substitute beneath themOperation tests run the real DLL guard, MO2 delays and log lifecycle against recording adapters. That is why 64% of the code is tests and the suite finishes in under three seconds.
  • unsafe is quarantinedThe main crate forbids it. All Win32 calls live in a 423-line helper where window handles are bound to their owning process and re-checked before every post. No unsoundness was found.
  • "Never kill FO4Edit" is enforced by the typeThe process trait has no kill method, so the contract cannot be broken by accident, and it is tested against a real child process.
  • Archives are built elsewhere, checked, then swappedA restore list is written before each move, with a crash round-trip test. The old archive is never deleted before the new one passes its check.
  • The installation lock is an OS lockNo PID file and no staleness heuristic, and aliased paths to the same install still contend.
  • Comments explain whyBatch line references, recorded divergences with their deciding issue numbers, and "do not simplify" warnings on each workaround. Most apparent oddities turned out to be documented decisions.
  • docs/episodes.md is an accurate record of the batchOf roughly thirty batch line citations spot-checked, all but a handful were exact. The ADRs are dated and amended in place. The exception is what they say about BSArch's own capability (P8).
  • Production code is disciplinedFour expect calls outside tests, each with a stated invariant, and a single lint suppression (a documented, test-conditional dead_code).

Method and limits

Five scoped reviewers read the code in parallel, one each for the process and Win32 layer, the tool adapters, the workflow engine, the CLI and intake path, and the documentation. Each was asked to try to disprove a finding before reporting it. I then re-read the code behind the findings marked verified and reproduced two on the debug binary. Three issues (B3, B4, B6) were reported independently by more than one reviewer.

Commands run: cargo test --workspace, cargo clippy --all-targets --workspace, cargo fmt --check, cargo audit, cargo tree -d, and the binary with --help, --version and several --dry-run forms.

Limits. No Fallout 4, Creation Kit, FO4Edit or MO2 run was performed, so the audit says nothing about whether a real build completes. Findings marked reviewed rest on one reader. The four required workarounds (FO4Edit window automation, MO2 delays, DLL renaming, Archive2 extract-repack) and the decisions recorded in the ADRs were treated as fixed and are not findings. Line numbers refer to commit 0178a3b.

Revision. The first version of this report treated ADR-0004, the glossary and episodes.md as the authority on BSArch and marked AGENTS.md and the README as wrong for saying it can append. The project owner corrected that. The usage text of the BSArch v1.1 installed beside xEdit on this machine confirms it: pack accepts an existing archive as a source. P1 was narrowed, and P8 and D8 were added. No BSArch pack was actually run.
